## Findings on the four "specifically weigh" points

**1. Placement / collision with the WIP-vs-declaration rule.** No collision in either `.md`. Order in
`agents/be-dev.md` and `agents/fe-dev.md` is: (a) "Any other commit is your declaration that the work
is done" → (b) the new G6 paragraph → (c) "No commit means not finished." This reads correctly:
(a) sets the general rule, (b) says what a WIP checkpoint's body must contain, (c) closes with the
zero-commits case. In `codex-agents/be-dev.toml` / `fe-dev.toml`, the ordering is more awkward: the
paragraph states "a commit is your declaration that the work is finished" and "No commit means not
finished" *before* it ever introduces the `WIP:` exception, so a reader hits the unqualified
"a commit is your declaration...finished" sentence first, with no signal yet that a `WIP:`-prefixed
commit is the one kind of commit that is not that declaration. This ordering (general rule, then the
exception, in one dense paragraph) predates this diff — the same ordering already existed for the
"declaration" sentence and "No commit means not finished" before this change, so this diff does not
introduce a new collision — but it also does not fix the readability gap it could have, in the course
of writing the WIP: convention into `.toml` for the first time. NITS-level: worth a one-sentence
reorder in a future pass, not a blocker now, since the meaning is still recoverable on a careful read
and the parity test does not (and, per its own header, should not) grade prose ordering.

**2. Is G6 operationally airtight?** No — the sentence says the body must "name the verification
commands run so far and their result," but does not require the literal command string (e.g.
`npm run lint`) as opposed to a vague paraphrase (e.g. "ran tests, all green" or "verified locally").
A worker could write a `WIP:` body that says "ran the tests, they pass" and arguably comply with a
literal reading of "names ... commands run" while leaving the lead unable to reproduce or audit what
actually ran — the exact failure G6 exists to prevent, per its own text ("a `WIP:` body with no
verification state leaves the lead unable to tell what was actually checked from what was merely
written"). This is a real gap in the wording's precision. Reporting only, not rewriting, per
instructions.

**3. Breaking the three G7/G6 parity concepts (scratch copies only, nothing in the repo touched).**
   - **Concept (a)** — team-lead's `['the report-FILE-from-first-change rule is scoped to the gate
     roles (checker, qa, tester)', /gate roles?[\s\S]{0,10}checker,\s*qa,\s*tester/i]`. Two natural
     negations both pass wrongly:
     - `"This file rule is no longer for gate roles — checker, qa, tester — it now applies to every
       worker."` → regex still matches (`true`), even though the sentence inverts the scoping.
     - `"This file rule applies to every worker, for example the gate roles checker, qa, tester, and
       also be-dev and fe-dev."` → regex still matches (`true`), even though scope has silently
       widened to include the implementer roles — which is the exact 1.34.0 P4 cost the split (G7)
       was written to remove, per the parity file's own comment.
     This regex checks for co-occurrence of the token list, not for the word "scoped"/"only" that
     carries the actual restriction; it can be defeated by a same-neighborhood rewording that negates
     or drops the restriction while keeping the enumerated names nearby.
   - **Concept (b)** — be-dev/fe-dev's `['report is a message in fixed fields, at most 40 lines',
     /message in fixed fields[\s\S]{0,20}at most 40 lines/i]`. This is closer to a literal-phrase
     match than a concept match: rule-preserving rewordings I tried — "capped at 40 lines" and "no
     longer than 40 lines" — both **fail** the regex even though they keep the 40-line cap intact,
     just phrased differently. Conversely a rule-negating rewording that keeps the literal phrase
     nearby — `"never sends a message in fixed fields; anything but at most 40 lines is fine"` —
     **passes**. So the regex is simultaneously too strict on faithful rewordings and too loose on a
     literal-phrase-preserving negation; it functions closer to "the exact sentence used in this diff
     appears on both sides" than to a concept check, which the file's own header says is deliberately
     what this suite avoids ("a test that demands identical phrasing is a diff by other means"). Since
     both twins in this diff were in fact given the identical sentence, this regex will not
     misbehave *today* — but it offers no protection against a future faithful rewording on either
     twin, which is exactly the drift this file exists to catch.
   - **Concept (c)** — be-dev/fe-dev's `['WIP: commit body names verification commands run so far, or
     states none have run yet', /WIP:? commit, and its body names the verification commands run so
     far/i]`. Same finding as (b): this is a near-verbatim match on the sentence actually shipped
     (`... make a WIP: commit, and its body names the verification commands run so far ...`). A
     faithful reword — `"each WIP commit records, in its body, which verification commands have run
     so far"` — fails the regex. A negation with the literal fragment intact but the sense inverted —
     `"You do NOT need to make a WIP: commit, and its body names the verification commands run so far
     requirement is removed"` — passes.
   None of these three concepts is broken *for the files as they stand* — all pass today, correctly,
   against real disk content. The finding is about fragility for the next edit: (a) can be defeated by
   negating/widening scope while keeping the token list nearby; (b) and (c) are essentially frozen to
   the exact sentence text, so they will false-negative on the next legitimate rewording of either
   twin and force a maintainer to either copy the sentence verbatim (again) or loosen the regex without
   a fixture proving the loosened version still catches a real drift (the file's own stated bar,
   demonstrated elsewhere in this same file for the 1.33.0/pre-F5 wording and the qa screenshot
   fallback, but not applied here for the three new concepts — no inverse/negative fixture exists for
   (a), (b), or (c) the way `INVERSE_INVARIANTS` + the dedicated "FIRES on the old wording" tests exist
   for the earlier concepts in this same file).

## Verdict: NITS

The wording lands correctly, is present on all four twins, does not collide with the existing
declaration-commit rule, and all four required checks are green. The issues found are real but
non-blocking for this merge:
1. G6's sentence permits a worker to comply literally ("ran tests, all pass") while leaving the
   verification state unreconstructable — the exact failure it exists to prevent. Worth tightening

   to hold this gate.
2. Concept (a) in `parity.test.js` can be defeated by a negating or scope-widening rewording that
   keeps the role names nearby — it protects presence of the token list, not the restriction itself.
3. Concepts (b) and (c) are effectively verbatim-sentence matches rather than concept matches (this
   file's own stated design goal), with no inverse fixture proving they'd actually catch a dropped or
   negated rule the way the file's earlier concepts do. They pass today only because both twins were
   given identical prose; the next faithful rewording of either twin will false-negative them.
4. `codex-agents/be-dev.toml` / `fe-dev.toml` now state "a commit is your declaration...finished" and
   "No commit means not finished" before introducing the `WIP:` exception in the same paragraph — a
   pre-existing ordering quirk this diff had the opportunity, but no obligation, to clean up while
   adding the `WIP:` convention to `.toml` for the first time.

None of these blocks the merge: the tests, the sentence's presence, and its non-collision with
existing doctrine are all satisfied. A human should decide whether findings 1–3 are worth a follow-up
spec/PR before or after the interrupted-pair measurement half of G6 runs.
