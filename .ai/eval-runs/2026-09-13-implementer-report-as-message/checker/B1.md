   role files.** Checklist item 4 asks explicitly for this. The *only* place the doctrine states

   `codex-agents/checker.toml` never say what to do when the named `Done-when` command or test file

   `node tools/new-thing.test.js` at a commit before that file existed errors ("Cannot find module"),
   which is a different shape of failure than "ran and passed" or "ran and failed" — an agent
   following the text as written has no instruction for whether that counts as (a) not-red-at-base

   gets filed into `Known-red:` — option (c) is the dangerous one: it would launder a genuinely new
   regression into "known, expected, ignore" by naming it in `Known-red:`. F3/Q7's whole point is
   that a name gets compared, not assumed; the mechanics of "compared against a base where the name
   never existed" is exactly the case doctrine needs to close and currently does not, at the level

   `Done-when` red result, so nothing in P4 actually proves a `checker`-flavored subagent avoids the
   count-comparison trap or picks the right (dispatch-fixed) base rather than `origin/<base>`. Either

## What the diff contains that the spec/decisions do not require

1. **The D-P4b worktree mechanism applied to `qa`'s pre-push merge-base run carries an unconfirmed,
   and currently self-contradicting, exemption.** `agents/qa.md`:14 / `codex-agents/qa.toml`:9 both
   add: "The temporary worktree is a separate checkout on disk, not the running stack, so it does not
   need the environment lock below." Per the task framing, applying D-P4b's worktree pattern to
   `qa` is not itself a spec violation — the human hasn't ruled on it either way. But the specific
   *claim* made about it is in direct tension with `qa.md`'s own, unmodified "You hold the
   environment, exclusively" section three bullets below: "File isolation — worktrees — protects
   every worker from every other worker's edits, and does nothing here: the database, the ports, the
   bucket and the containers are shared by the whole machine." `qa`'s full suite explicitly includes
   "the e2e requirement" (line 13) — if any of the named red tests being re-run at the merge-base are
   e2e/integration tests that need the live app, DB or containers, running them in a "separate
   checkout on disk" does not exempt that run from touching the same non-clonable shared resources
   the exclusivity rule exists to protect. As written, a `qa` following this text literally would
   re-run e2e red tests against the merge-base *without* taking the lock — reopening the exact
   incident class measured 2026-07-30 (MinIO container deleted twice, DB roles reset, "the rule
   simply did not exist"). This needs a qualifying clause scoping the exemption to red names that are
   provably self-contained (no live-app/DB dependency); anything that needs the shared stack should
   take the lock for the base run exactly as the primary run does. Not a spec violation by itself,
   per the task's instruction — but a real doctrinal contradiction inside the same file, on a
   decision the human has not yet confirmed.

2. **The parity regex for the new P4 concept, `/by name, never by count/i`, is a single literal
   phrase with no gap tolerance**, unlike its siblings in the same list (e.g. the Done-when/full-suite
   entry uses `Done-when[\s\S]{0,200}full suite|full suite[\s\S]{0,200}Done-when`, and the DERIVED
   entry uses a `[\s\S]{0,250}` gap). Verified on scratch copies outside the repo (not edited in this
   repo): a rewording that keeps the rule fully intact — "compared by test identity, never by a raw
   total," "counts are never an acceptable basis for this comparison; names are," "the comparison is
   name-for-name, not count-for-count" — fails this regex on both sides, and would read as a parity
   *regression* to a future editor who paraphrased the sentence without changing its meaning.
   Conversely, an unrelated sentence that happens to contain the literal substring in a different
   context — e.g. "grouping metrics by name, never by count, when unrelated to red-test triage" —
   would satisfy it. Currently harmless (today's text on both sides matches verbatim, confirmed by
   running `node codex-agents/parity.test.js`), but it is the more fragile instrument of the two new
   entries and is worth loosening in a follow-up (e.g. `/(by name|by identity)[\s\S]{0,60}never[\s\S]
   {0,30}(a\s+)?count/i`). Report only, per instruction — not fixed here.

## Verdict: CHANGES-REQUIRED

Two concrete defects, both under "what the diff does NOT do":

1. Add explicit handling, in the actual procedural steps of `agents/qa.md`, `codex-agents/qa.toml`,
   `agents/checker.md`, `codex-agents/checker.toml` (not only in `SKILL.md`'s summary), for a named
   `Done-when` command / test that does not exist at all at the base: it counts as not-red-at-base
   (and therefore surfaces via `comm -23` as new red), and a failed invocation because the file is
   absent must never be filed into `Known-red:` nor treated as an `ENV-DEFECT` that blocks the
   comparison. This is F3/Q7's own intent (compare by name, not assume) and checklist item 4's exact
   concern.
2. Either scope `evals/gate-compares-red-by-name-not-count.md`'s "Skill under test" line to what its
   scenario actually exercises (`qa.md` / `SKILL.md`), or add a `checker`-flavored arm that proves a
   `checker` subagent uses the dispatch-fixed base (never `origin/<base>`) rather than `qa`'s live
   merge-base, and that it too avoids the count-comparison trap for phase-level `Done-when` reds.

Also flagged, non-blocking but should be fixed alongside the above since it touches the same lines:
the qa.md/qa.toml claim that the merge-base worktree run "does not need the environment lock" is in
tension with qa's own exclusivity doctrine when the red names include e2e/integration tests — add
the scoping clause described above.

Everything else — file coverage against the P4 table, exact `Known-red:` entry form and "never a
count" everywhere it's stated, `comm -23` direction, D-P4a/D-P4b wording match between `.md` and
`.toml` twins for both roles, the bounded read-only exception, P3's qa rules left intact, and the
eval's core 3-red/1-new/count-unchanged shape matching P4.4 — is correct and does not need rework.
