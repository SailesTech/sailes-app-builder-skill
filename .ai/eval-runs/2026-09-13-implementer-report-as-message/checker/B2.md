## Adversarial test on the parity regex (checklist item 5 — scratch files only, nothing in the repo touched)

```js
const RE = /(?=[\s\S]*?merge-base)(?=[\s\S]*?comm -23)/i;

// Drops the actual rule (compares by COUNT, the exact thing F3/Q7 forbid) while keeping both literal
// command tokens nearby for "historical audit" flavor text — still matches.
RE.test(`When the full suite has red tests, compare the total red count on the branch against the
total red count recorded the last time the suite ran at git merge-base. If the counts match, treat it
as no regression and proceed. (For historical audit only, a \`comm -23\` diff of the two name lists is
available in the release-checklist appendix, but is not required for the gate decision.)`)
// → true
```
This regex is the **only** invariant in `codex-agents/parity.test.js` that uses an unbounded
`[\s\S]*?` lookahead; every sibling invariant that spans two concepts bounds the gap (`{0,120}`,
`{0,250}`) specifically so an unrelated, distant mention of one of the two tokens can't manufacture a
false pass. This one has no bound at all, and — more importantly — it never actually tests for "by
name" or "never by count," only for the two literal shell-command substrings `merge-base` and
`comm -23`. The file's own header comment says these regexes are "intentionally loose on wording and
strict on concept, ... this checks that both still make the same promise, not that they use the same
words" — for this one entry, that promise isn't actually checked: two documents could each mention
`merge-base` and `comm -23` in service of a **count**-based rule (the one thing this whole phase exists
to forbid) and this parity check would still print `ok`. The doctrine text as currently written is
correct in both twins, so this does not produce a wrong verdict today — but it is a hole in the very
guardrail Done-when names as this phase's regression protection, for exactly the regression the phase
is about. Recommend requiring `never|by name` and `count` to co-occur with the existing tokens, and/or
bounding the lookahead like its siblings, in a follow-up — reported per instructions, not fixed here.

I also checked for over-tight false negatives (a rewording that keeps the rule but fails the check):
whitespace/hyphenation variants (`comm  -23` double space, `mergebase` without a hyphen) do fail the
regex, but these track the literal shell syntax of the commands themselves (`git merge-base`, `comm
-23`), which a real prose edit is unlikely to respell — a much lower-risk failure mode than the
false-positive above.
